Does what fills the padding change how fast an MoE model trains? LoRA on 4 GPUs

main-v1.1 · Nemotron 3 Nano 30B-A3B · LoRA fine-tuning on Nemotron IF-Chat · 4× H100 · runs finished {{date}}

Why this experiment. main-v1 asks the same question with full-parameter training on all 8 GPUs of a node, but one GPU's cooling failed before it finished. Full-parameter training of this 31.6B-parameter model does not fit on the 4 healthy GPUs, so main-v1.1 repeats the whole comparison with LoRA on 4 GPUs. It answers the same question in a second setup; its numbers are not interchangeable with main-v1's.

Question. Conversations in a batch have different lengths, so the shorter ones are filled up with padding tokens. Nemotron 3 Nano's mixture-of-experts (MoE) layers compute on padding tokens like real ones, and with the standard padding they all go to the same few experts. Can we train faster by changing what the padding contains, or by moving experts between GPUs?

Answer. Yes, and the methods rank the same way as in main-v1, with about half the effect. With every micro-batch padded to 8,192 tokens ({{fixed.default.pad}} of the tokens are padding), visible natural text cut the step time by {{fixed.natural_visible.abspct}} and expert placement by {{fixed.placement.abspct}}. With each micro-batch padded only to its longer conversation ({{batchmax_pass2.default.pad}} padding), expert placement cut it by {{batchmax_pass2.placement.abspct}} and the other methods by about 2%.

In the first pass, where one-time setup for new lengths more than doubles the step time ({{batchmax_pass1.default.step}}), every method saves about 1%.
  • Why the savings are smaller than in main-v1. With the experts split over 4 GPUs instead of 8, the default's imbalance is milder: the busiest GPU does {{fixed.default.imb}} the average GPU's expert work at fixed length, against {{ref.fixed.default.imb}} in main-v1, so there is less to fix. Within each setting, the method with the least uneven worst case is the fastest: visible natural text at fixed length, expert placement in the longest-in-batch setting.
  • Padding less still beats every padding trick. Longest-in-batch padding with the default method reaches {{batchmax_pass2.default.umfu}} useful MFU in the second pass, more than the best fixed-length method ({{fixed.natural_visible.umfu}}). No method changes what the model learns: per-step losses differ from the default by at most {{loss.max}}.

Setup

ModelNVIDIA Nemotron 3 Nano 30B-A3B (BF16). 52 layers: 23 MoE layers, 23 Mamba layers and 6 attention layers. Each MoE layer has 128 experts (small feed-forward networks); a router sends every token to 6 of them, plus one shared expert that every token uses.
Hardware{{setup.world}} H100 80 GB GPUs (GPUs {{setup.gpus}} of an 8-GPU node, all on one NUMA node). Each GPU holds {{setup.experts_per_gpu}} of the 128 experts of every MoE layer (expert parallelism): tokens travel to the GPUs that hold their experts and back, and each MoE layer waits for the GPU with the most work. All other weights are split across the {{setup.world}} GPUs (FSDP2).
TrainingLoRA fine-tuning with AutoModel, using the settings of AutoModel's Nemotron Nano 3 LoRA example: rank-8 adapters on the attention, Mamba input and shared-expert layers (5.7 million trainable weights, 0.02% of the model). Everything else, including the 128 routed experts per layer, stays frozen but still runs forward and backward. 128 conversations per optimizer step: each GPU runs {{setup.microbatches}} micro-batches of 2 conversations. Adam, learning rate 10−5 with warm-up and cosine decay, activation checkpointing, loss on assistant tokens only.
DataThe same {{data.rows}} conversations as main-v1, in the same order: drawn at random from Nemotron-Instruction-Following-Chat-v1 (split chat_if, {{data.source_rows}} conversations), formatted with the Nano 3 chat template and cut at 8,192 tokens ({{data.truncated_pct}} are cut). Median length {{data.median_tokens}} tokens, mean {{data.mean_tokens}}.
ProtocolEvery run starts from the same weights and trains on the same conversations in the same order, so step n of every run sees exactly the same data. Runs go one at a time on the same 4 GPUs, each after a 20-second load test of those GPUs. Fixed length: 40 steps (one pass over the data). Longest in batch: 80 steps (two passes). In each setting the default method runs first and again last, to measure how much two identical runs differ.

With longest-in-batch padding, micro-batch lengths vary. The first time a GPU sees a length, some kernels (attention in particular) build an execution plan for it. In the first pass over the data, {{batchmax_pass1.newlen}} of micro-batches have a length their GPU has not seen before, and a default step takes {{batchmax_pass1.default.step}}. The second pass over the same data reuses the plans and takes {{batchmax_pass2.default.step}}.

Padding never counts toward the loss, and it always comes after the real tokens. Attention only looks backward, so real tokens never see the padding, even when it is visible. Every method therefore trains the same model on the same loss: the largest per-step loss difference from the default is {{loss.max}}. Expert placement only changes which GPU holds which expert, not what the model computes. It was computed from the default run's expert usage on this same data, so it is a best case.

How we measure

  • Step time: wall-clock time of one optimizer step ({{setup.microbatches}} micro-batches forward and backward, plus the update). The first 2 steps of each pass are left out because they include one-time setup.
  • Useful MFU (model FLOPs utilization): the arithmetic of full training for the real tokens only, divided by the step time and by the GPUs' peak BF16 throughput (989 TFLOP/s each). LoRA skips part of that arithmetic (the gradients of the frozen weights), so here MFU is a throughput measure in full-training units: comparable between methods, not with main-v1 and not a measure of how busy the GPUs are.
  • Busiest GPU's expert work: in each MoE layer and micro-batch, the token-to-expert assignments handled by the busiest GPU divided by the average GPU, averaged over layers and micro-batches. 1.0 is perfectly even; with 4 GPUs, 4.0 would mean one GPU does all the expert work.
  • Comparison: every run sees the same data at every step, so each method is compared with the default run at the same steps. We report the mean of these per-step differences with a 95% confidence interval.

Both setups rank the methods the same way at fixed length, and main-v1.1's savings are about half of main-v1's. Two things change between the setups (LoRA and the 4-way expert split), so this comparison cannot say how much each contributes. The milder default imbalance with 4 GPUs is consistent with the smaller savings: every method starts from less unevenness to remove. In main-v1, three longest-in-batch runs were lost to the GPU fault.

Why the methods help: how evenly the expert work is spread

For each MoE layer and micro-batch: the expert work of the busiest GPU divided by the average GPU's, then averaged (1.0 is perfectly even; with 4 GPUs the worst possible is 4.0). With default padding, all padding tokens of a micro-batch go to the same 6 experts: {{fixed.default.top6}} of their expert assignments land on the 6 most used experts of each layer, against {{fixed.default.realtop6}} for real tokens. Random tokens and hidden natural text spread the padding over more experts ({{fixed.random.top6}} and {{fixed.natural_masked.top6}} on the top 6). Expert placement puts the busy experts on different GPUs. Visible natural text is routed like real text ({{fixed.natural_visible.top6}} on the top 6). The average does not settle placement against visible natural text; the most uneven micro-batches ("worst" in the table) do: {{fixed.natural_visible.imbworst}} against {{fixed.placement.imbworst}} at fixed length, {{batchmax_pass2.placement.imbworst}} against {{batchmax_pass2.natural_visible.imbworst}} for longest in batch, matching which of the two is faster.

Caveats

  • This is a second setup, not a replacement for main-v1: LoRA instead of full-parameter training, and the experts split over 4 GPUs instead of 8. Both change how much of each step is expert work and how uneven it can be.
  • Expert placement was computed from the default run's expert usage on the same data it was then tested on. That makes it a best case. A real system would have to plan from earlier batches.
  • One run per method. Two identical default runs differed by {{fixed.default_repeat.pct2}} ({{fixed.default_repeat.ci2}}) at fixed length and by {{batchmax_pass2.default_repeat.pct2}} ({{batchmax_pass2.default_repeat.ci2}}) in the longest-in-batch second pass, well below every method's effect.
  • These are short runs (40 and 80 steps) that measure speed, not model quality.
