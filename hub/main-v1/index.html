Does what fills the padding change how fast an MoE model trains?

Nemotron 3 Nano 30B-A3B · full fine-tuning on Nemotron IF-Chat · 8× H100 · runs finished 2026-09-27

Question. Conversations in a batch have different lengths, so the shorter ones are filled up with padding tokens. Nemotron 3 Nano's mixture-of-experts (MoE) layers compute on padding tokens like real ones, and with the standard padding they all go to the same few experts. Can we train faster by changing what the padding contains, or by moving experts between GPUs?

Answer. Yes, when padding is a large share of the tokens. With every micro-batch padded to 8,192 tokens (59% of the tokens are padding), filling the padding with visible natural text cut the step time by 22.9%, and spreading the busy experts over the GPUs cut it by 18.4%. With each micro-batch padded only to its longer conversation (30% padding), random padding tokens cut the steady-state step time by 5.8%.

  • Fixed length. Default: 15.30 s per step. Natural text, visible: 11.80 s (−22.9%). Expert placement: 12.48 s (−18.4%). Natural text, hidden: 13.57 s (−11.3%). Random tokens: 13.75 s (−10.1%). Two identical default runs differed by +0.2%.
  • Why. With default padding, every padding token of a micro-batch goes to the same 6 experts, so the busiest GPU does 2.18× the average GPU's expert work and the other GPUs wait for it. Expert placement and visible natural text bring this down to 1.18× and 1.21× and save the most. Random tokens and hidden natural text spread the padding only partly (1.71×, 1.68×) and save about half as much.
  • Longest in batch. The imbalance is milder (1.64×). Random tokens save 5.8% of the steady-state step time (11.08 s → 10.44 s), and 3.1% in the first pass, where one-time setup for new lengths doubles the step time. Expert placement's second pass and both natural-text methods have not been measured in this setting yet (GPU fault; see Caveats).
  • Padding less beats every padding trick. Longest-in-batch padding with the default method reaches 9.79% useful MFU in steady state, more than the best fixed-length method (9.20%).
  • Same training. No method changes what the model learns: per-step losses differ from the default by at most 0.0007, on losses between 0.27 and 0.57.

Setup

ModelNVIDIA Nemotron 3 Nano 30B-A3B (BF16). 52 layers: 23 MoE layers, 23 Mamba layers and 6 attention layers. Each MoE layer has 128 experts (small feed-forward networks); a router sends every token to 6 of them, plus one shared expert that every token uses.
HardwareOne node with 8× H100 80 GB. Each GPU holds 16 of the 128 experts of every MoE layer (expert parallelism): tokens travel to the GPUs that hold their experts and back, and each MoE layer waits for the GPU with the most work. All other weights are split across the 8 GPUs (FSDP2).
TrainingFull-parameter fine-tuning with AutoModel. 128 conversations per optimizer step: each GPU runs 8 micro-batches of 2 conversations. Adam, learning rate 10−5 with warm-up and cosine decay, activation checkpointing, loss on assistant tokens only.
Data5,120 conversations drawn at random from Nemotron-Instruction-Following-Chat-v1 (split chat_if, 426,009 conversations), formatted with the Nano 3 chat template and cut at 8,192 tokens (12% are cut). Median length 2,392 tokens, mean 3,364; 3.3 user turns on average; 64% with reasoning off.
ProtocolEvery run starts from the same weights and trains on the same conversations in the same order, so step n of every run sees exactly the same data. Runs go one at a time on the same 8 GPUs. Fixed length: 40 steps (one pass over the data). Longest in batch: 80 steps (two passes, explained below). In each setting the default method runs first and again last, to measure how much two identical runs differ.

Padding never counts toward the loss, and it always comes after the real tokens. Attention only looks backward, so real tokens never see the padding, even when it is visible. Every method therefore trains the same model on the same loss: the largest per-step loss difference from the default is 0.0007. Expert placement only changes which GPU holds which expert, not what the model computes. It was computed from the default run's expert usage on this same data, so it is a best case (see Caveats).

Why padding can slow training down

The MoE layers of Nemotron 3 Nano do not skip padding: the router picks 6 experts for every padding token, and those experts compute on it. Hidden padding tokens do not mix with any other token, so each one reaches the router carrying only its own token. When every padding token is the same token, all of them are routed to the same 6 experts. The GPUs holding those experts get far more work than the others, and every MoE layer waits for them. The methods attack this in three ways: make padding tokens differ from each other (random tokens, natural text hidden), let padding read like normal text (natural text visible), or spread the busy experts over more GPUs (expert placement).

How we measure

  • Step time: wall-clock time of one optimizer step (8 micro-batches forward and backward, plus the update). The first 2 steps of each pass are left out because they include one-time setup.
  • Useful MFU (model FLOPs utilization): the model's arithmetic for the real tokens only, divided by the step time and by the 8 GPUs' peak BF16 throughput (989 TFLOP/s each). Padding counts as zero useful work. Padded MFU also counts padding tokens as work; it is the number AutoModel reports by default.
  • Busiest GPU's expert work: in each MoE layer and micro-batch, the token-to-expert assignments handled by the busiest GPU divided by the average GPU, averaged over layers and micro-batches. 1.0 is perfectly even; 8.0 would mean one GPU does all the expert work.
  • Comparison: every run sees the same data at every step, so each method is compared with the default run at the same steps. We report the mean of these per-step differences with a 95% confidence interval.

Why the methods help: how evenly the expert work is spread

For each MoE layer and micro-batch: the expert work of the busiest GPU divided by the average GPU's, then averaged. The dashed line is a perfectly even split. With default padding, all padding tokens of a micro-batch go to the same 6 experts: 100% of their expert assignments land on the 6 most used experts of each layer, against 13% for real tokens. Random tokens and hidden natural text spread the padding over more experts (58% and 58% on the top 6). Expert placement keeps the 6 busy experts but puts them on 6 different GPUs. Visible natural text is routed like real text (13% on the top 6).

Caveats

  • Expert placement was computed from the default run's expert usage on the same data it was then tested on. That makes it a best case. A real system would have to plan from earlier batches and would miss some changes.
  • One run per method. Two identical default runs differed by +0.15% (−0.04% to +0.34%) in the fixed-length setting, far less than any method's effect there.
  • At 02:58 UTC one GPU's cooling failed: under load it ran at 85–91 °C and throttled to about 60% of its normal speed, which slows every step. Steps that overlap the overheating are left out of all numbers (runs table below). The experiment is paused until the GPU is repaired. Still to run in the longest-in-batch setting: expert placement (both passes again), natural text hidden and visible, and the repeated default run, about 1.5 hours. Each run now starts only after a 20-second load test of every GPU passes.
  • One node, 8 GPUs, 2 conversations per GPU per micro-batch. The gains depend on how much of each step is expert work and how uneven that work is. More padding per micro-batch makes the methods matter more.
  • These are short runs (40 and 80 steps) that measure speed, not model quality. The training loss is the same for every method by construction.
